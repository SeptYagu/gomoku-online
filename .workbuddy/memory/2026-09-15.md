## 项目定位纠偏：gomoku-online 是面向公众的商业化站点

**触发**：用户问「有没有加 feedback 页面」，我首轮把它当成个人自用项目权衡，建议砍掉
`docs/FEEDBACK_AND_LOG_COLLECTION_PLAN.md` 的 F0/F1/F3/F4，只做轻量反馈表单。用户当场纠正：
「这个项目不是个人自用项目，是将要面向公众的项目，请重新理解文档」。误判根因是
MEMORY.md 里「单人项目直接提交 main」被读成了「个人自用」——它只描述协作方式。

**重新核对的事实**（依据 `WEBSITE_BUILD_PLAN.md`、`README.md`、`STATUS.md`、`docs/M3_PUBLIC_TEST_PLAN.md`）：
- 公开测试站已上线 `http://gomoku.yagu.ddns-ip.net`；build plan 第 1/7 节写明商业目标是
  AdSense / Google H5 Games Ads 变现 + SEO 自然流量；README「复用原则」写明商业发布优先。
- 进度位于「阶段 3 功能已完成 → 阶段 4 广告变现与合规未开始」的窗口。
- 合规页面缺口：`src/app` 只有 `[locale]/page.tsx`、`[locale]/profile/[playerId]/page.tsx`、
  `(root)/page.tsx`、`api/version/route.ts`；**无 Privacy Policy / Terms / Cookie Notice /
  Contact / About**，无 `ads.txt`，字典 `ads` 键仅为占位（"Future ad placement"，
  `src/i18n/dictionaries.ts:447`）。
- Feedback 实现为零：无 `/{locale}/feedback` 路由、无 `POST /api/feedback`、
  `tools/` 无 sync-feedback、`package.json` 无 `sync:feedback`。
  全仓 `feedback` 命中仅 3 处且无关（`COPY_FEEDBACK_DURATION_MS` 复制提示时长）。
- `docs/M3_PUBLIC_TEST_LOG.md` 5 条记录全部是开发机/命令行脚本产出，**零真实用户反馈**。

**对计划的新评估**（修正上一轮建议）：该计划对匿名公开站点**不是过度设计**——
匿名 + 附件上传必须做 magic bytes 校验/像素上限/流式 6MiB 限制/限流/同源校验，
用户数据（邮箱+日志+截图）必须脱敏 + 保留期限。F3/F4 可延后但不应取消。

**发现的计划自身缺口**（面向公众视角新增的洞见）：
1. 顺序倒置：表单要收邮箱+日志+截图，隐私政策却写成「后续需说明」——隐私政策与同意机制
   必须先于表单上线。且计划缺少 consent 勾选与隐私政策链接的强关联。
2. 反自动化不足：仅 IP 限流（5 次/10min、20 次/天），公网匿名上传还缺总配额 + 磁盘水位 +
   人机验证（Turnstile）或蜜罐。
3. 数据主体权利缺失：GDPR/CCPA 下用户如何要求删除自己提交的反馈（含邮箱、截图）未定义。
4. 反馈页未规划 `noindex`（计划文档亦未提），会污染 SEO。
5. 建议把 `/{locale}/feedback` 直接当作 build plan 阶段 4 要求的 Contact 页，不再另做一份 Contact。

**本轮未改任何源码**，只做了分析与记忆纠偏。下一步批次待用户确认。

## 对 `FEEDBACK_AND_LOG_COLLECTION_PLAN.md`（251 行）的漏洞审查

**审查前核实的技术前提**（本仓实测，非推测）：
- 全部 `/api/*` 都是**自定义 server 的 raw http handler 手写**（`src/server/online-server.ts:25-47` 的
  `if (handleXxxApi(...)) return;` 链），只有 `/api/version` 是 Next route handler。
  → 反馈接口应沿此模式在 `IncomingMessage` 上做流式解析（可行，且无 Next body 限制）。
- ⚠️ **`readJsonBody`（`online-server.ts:230`）不能复用**：它 `request.setEncoding("utf8")` +
  字符串拼接 + 上限 4096，二进制截图经它会被 UTF-8 解码破坏。
- 可复用设施：`FixedWindowRateLimiter`（`src/server/rate-limit.ts`，单窗口，双窗口需两个实例）、
  `resolveClientAddress`（`client-address.ts`，仅 loopback peer + trustProxy 才采信 XFF 末位）、
  `randomBytes().toString("base64url")`（`accounts.ts:518`，URL-safe，可做 feedbackId/artifactId）。
- **依赖里没有 busboy / formidable / sharp / jimp**。计划要求"流式 multipart parser"与
  "解码后重新编码为安全图片"，均无选型，而 AGENTS.md §1.1 严禁未评估引入重量级库。
- **`.gitignore` 未覆盖新目录**：只有 `data/game-records/`、`data/accounts/`；有 `*.log`
  但计划日志用 **`.jsonl`** 后缀，绕过了该规则 → 反馈（含邮箱/截图/日志）会被 `git add -A` 带走。
- **站点现状是纯 HTTP**：`deploy/openresty-gomoku.conf.example:5` 只有 `listen 80`，
  README/M3 用 `http://gomoku.yagu.ddns-ip.net`，无 TLS 配置。

**最硬的一条**：§1 目标宣称"只下载本地尚不存在或**校验不一致**的文件"，但 §5 同步算法
第 3 步仅比对「状态记录里的 sha」与清单 sha，**从不校验已存在本地文件的实际内容**，
第 5 条也只对新下载文件校验 → 本地文件在 size 不变时被篡改/损坏，永远不修复；
而 §8 验收标准却要求"篡改一个文件后只修复该文件"。**目标、算法、验收三者互斥**。

**P0**：① `.gitignore` + `.jsonl` 后缀 → PII 进库风险；② HTTP 现状与计划 HTTPS 假定冲突
（Bearer token / 邮箱 / 截图明文传输），且 HTTPS 未列为前置条件。
**P1**：③ 上述同步算法自相矛盾；④ §7 F0–F5 **无任何阶段实现保留期清理**，而 §6 已承诺
30/180 天保留；⑤ §8 验收不含"隐私政策存在 + consent 勾选"，无隐私政策也能"验收通过"；
⑥ 图像处理与 multipart 解析零选型；⑦ 未要求剥离 EXIF/GPS；⑧ Origin 校验基准未定义，
照抄本仓 `new URL(request.url, request.headers.host)` 习惯会被 `Host: evil.com` 绕过。
**P2 要点**：诊断日志"只覆盖当前 tab"→ 多标签场景恰好丢掉出问题 tab 的日志，采集价值近零；
`.tmp` 残留目录无回收者；清单 `createdAt` 权威来源未定义（mtime 会漂移破坏分页游标）；
限流键依赖反代在 loopback（`client-address.ts:31`），非 loopback 反代会让全站共享同一配额；
无幂等键；无新反馈通知（公测反馈可能数日无人看）；GDPR/CCPA 删除权无入口；`Digest` 头已废弃
（应为 `Content-Digest`）；字符计数口径未定义且 10 字符下限会挡掉短反馈；缺 dark mode 验收；
反馈页无 `noindex`；内容处置/违法内容上报义务未定义；未衔接"build 静态预渲染 + 启动快照模式"
两条既有约束。
