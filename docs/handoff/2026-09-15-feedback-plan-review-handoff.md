## 3. 缺陷清单

### 3.1 P0（上线前必须封堵，涉及不可逆泄露）

#### P0-1 `.gitignore` 未覆盖新增数据目录，且 `.jsonl` 后缀绕过了现有的 `*.log` 规则

`.gitignore` 逐条列举数据目录，只忽略了 `data/game-records/` 与 `data/accounts/`，**没有 `data/feedback/`，也没有 `data/runtime-logs/`**；同时计划规定日志使用 `.jsonl` 后缀，而唯一的通用日志规则是 `*.log`，对该后缀完全无效。

计划 §3.3 仅在正文写了一句「反馈目录、运行日志和同步状态必须加入 `.gitignore`」，**未将其列为 F0 阶段的验收项**。后果：`data/feedback/` 内含用户邮箱、反馈正文、客户端诊断日志，一旦被 `git add -A` 携带进版本库即进入 Git 历史，**无法通过删除文件撤回**。

> 注意 `data/` 下 `data/openings/generated/*.sgf` 是运行时要读的资产、必须留在版本库内，因此**不能用 `data/*` 一刀切**，必须显式追加 `data/feedback/` 与 `data/runtime-logs/` 两条。

#### P0-2 站点现状为纯 HTTP，而计划以 HTTPS 为前提却未将其列为前置条件

实测 H 表明当前部署形态是 `listen 80` 的明文 HTTP，仓库内不存在任何 TLS 配置，公开地址也是 `http://`。而计划：

- §4.2 通过 `Authorization: Bearer <GOMOKU_LOG_EXPORT_TOKEN>` 拉取反馈 artifact（含 `metadata.json` 中的 `message` 与 `email`）；
- §3.1 让用户在浏览器表单中填写邮箱、上传截图；
- §4.4 却直接断言「生产环境只允许 HTTPS，并在 OpenResty 层追加请求速率限制」。

即计划把一个**尚不存在的环境**当成了既定事实。在 HTTP 页面上收集个人数据、并以明文传输管理凭据，属于直接的个人数据泄露通道。**「HTTPS 先行」必须上升为该计划的显式前置条件与 F2 的准入门槛**，而不是散落在 §4.4 的一句期望。

### 3.2 P1（设计自相矛盾，或声称的能力不成立）

#### P1-1 目标、算法与验收标准三者互斥（本次审查最严重的设计缺陷）

- §1 目标原文：「工具只下载本地尚不存在或**校验不一致**的文件。」
- §5 算法第 3 步：「若本地目标存在、size 相同且本地状态记录的 SHA-256 相同，则跳过。」
- §5 算法第 4 步：仅在**状态缺失或不一致**时才计算本地 SHA-256。
- §5 算法第 5 步：只对**新下载**的文件做 size 与 SHA-256 校验。
- §8 验收标准：「篡改一个文件后只修复该文件。」

问题：算法**从不校验已存在本地文件的实际内容**。跳过判定完全依赖「同步状态文件里记录的 sha」与清单 sha 是否一致，与本地文件真实内容无关。因此当本地文件被篡改、被截断替换、或磁盘静默损坏而 **size 恰好不变**时，第 3 步直接跳过，永远不会被修复——这既违背 §1 承诺的「校验不一致」，也使 §8 的验收条目**在算法下不可达**。

修复方向：跳过条件必须是「本地文件重算 SHA-256 与清单一致」。若出于性能考虑要保留快速路径，则至少应对「状态记录存在但本地 mtime/size 与状态记录不符」的项强制重算，且验收标准需补一条 size 不变的篡改用例。

#### P1-2 承诺了数据保留期，但没有任何阶段实现清理任务

§6 向用户与隐私政策承诺：「服务端运行日志 30 天、反馈及附件 180 天」，并称「具体清理策略通过环境配置」。但 §7 的 F0–F5 六个阶段全部读下来，**没有任何一个阶段承接清理任务的实现**，F0 列的是存储/校验/路径/索引，F5 只写「备份/权限/容量监控和保留策略」的文档更新。

声明保留期限却不实现删除，与隐私政策的承诺直接冲突（GDPR 存储限制原则）。**必须新增负责者**（并入 F0 存储基础或单列 F6），并把「超过保留期的已完成目录被删除且记录数量」写成可验证的验收项。

#### P1-3 验收标准不含隐私合规项，因此「全部通过」仍可在无隐私政策下上线

§8 的功能验收与质量门禁中，**没有任何一条要求「隐私政策页面存在且被表单链接」或「提交前需勾选同意」**。§3.1 的表单字段列表里也**没有 consent 字段**，§6 只写「后续隐私政策需说明用途与保留期限」。

结论：按这份验收标准，一个收集邮箱、诊断日志与截图的公开表单，可以在零隐私政策、零同意机制的前提下被标记为「验收通过」。这对面向六语国际用户（含欧盟）的公开站点是实质性合规缺口。修复方向：隐私政策页面上线并链接、表单增加必选同意项，两者都写进 F2 验收。

#### P1-4 图像处理与 multipart 解析零选型，而这是全计划最重的两个技术决策

实测 F 表明依赖清单里没有任何 multipart 解析器与图像库。而 §4.1 要求：

- 「使用流式 multipart parser，超限立即停止读取并清理临时目录，不把附件整体读入内存」——**解析器未选型**；
- 「截图须检查 magic bytes、限制解码后的像素尺寸，并**解码后重新编码为安全图片**」——Node 不具备内置图像解码能力，**该句在没有图像库时无法实现**。

两者都触碰 `AGENTS.md` §1.1「严禁未经评估引入第三方重量级库」的红线，计划却把决策留空。另需注意实测 B：**照抄现有 `readJsonBody` 处理附件会破坏二进制数据**，这条陷阱计划未提示，实现者极易踩中。

> 其中「图像库」一项已被本轮决策消解，见 §4；但「multipart 解析器」在保留 `clientLog` 附件的前提下依然成立，必须显式决策。

#### P1-5 未要求剥离 EXIF/GPS 元数据

§4.1 只写「重新编码为安全图片」，未明确**剥离 EXIF 等元数据**。用户用手机上传的截图或照片可能夹带 GPS 精确定位，一旦落盘即成为维护者可读的位置信息，属于计划自身未识别的隐私风险。

> 该缺陷随本轮「取消图片上传」决策一并消解，见 §4。

#### P1-6 Origin 同源校验的基准未定义，照抄本仓既有习惯会被绕过

§4.1 要求「只接受同源浏览器请求（校验 `Origin`/`Sec-Fetch-Site`）」，但**未规定同源基准的来源**。而本仓既有写法是拿请求 Host 头作为 URL 基准（实测 A：`src/server/online-server.ts:59/131/148/165/182` 的 `new URL(request.url ?? "/", "http://" + request.headers.host)`）。

若实现者沿用该习惯去比对 `Origin` 与请求 Host，则攻击者只需发送 `Host: evil.com` 搭配 `Origin: evil.com` 即可让校验自行通过。**必须规定基准来自服务端配置的权威 origin（环境变量），而非请求头。**

### 3.3 P2（实质问题，可缓解但不应放行）

| 编号 | 缺陷 | 说明与证据 |
| :--- | :--- | :--- |
| P2-1 | 诊断日志「只覆盖当前 tab」，恰好丢掉出问题 tab 的记录 | §3.2 限定日志仅覆盖当前 tab 会话，§3.1 又在反馈页展示该 tab 的日志。用户在多标签对局中遇到问题、另开反馈页提交时，采集到的是**反馈页自己那个 tab** 的日志，排障价值接近零。应改为跨 tab 共享（BroadcastChannel/sessionStorage）或在 UI 明确声明范围 |
| P2-2 | 孤儿 `.tmp` 目录无回收者 | §3.3 用 `<feedbackId>.tmp` 目录 + 原子 rename，但 §6 清理任务只「删除已完成目录」。进程在写 tmp 中途崩溃后残留的临时目录**永不回收**，造成磁盘泄漏 |
| P2-3 | 清单 `createdAt` 的权威来源未定义 | §4.2 以 `(createdAt, artifactId)` 为分页排序键，若 `createdAt` 取自目录 mtime 或扫描时刻，跨机同步/rsync/备份恢复都会改变它，游标分页将出现漏项或重复项。应规定其取自 `metadata.json` 中不可变的 `receivedAt`；`runtime-log` 类 artifact 的来源同样未定义 |
| P2-4 | 限流在一种常见配置下整体失效，且计划未写该前置条件 | 限流键依赖实测 D 的 `resolveClientAddress`：仅当**对端为 loopback** 且 `GOMOKU_TRUST_PROXY=1` 时才采信 XFF。若反代不在本机 loopback（例如另一台机器），解析退化为全部请求同键 → **全站共享「每 10 分钟 5 次」配额**，反馈接口直接不可用。另需注意限流器为固定窗口，窗口交接处允许 2× 突发 |
| P2-5 | 无幂等键 | §3.1 只承诺失败时「不自动重复上传」，但挡不住用户双击提交或主动重试 → 产生重复反馈目录、浪费磁盘与运维注意力。应引入客户端生成的 `submissionId` 做幂等 |
| P2-6 | 无新反馈通知机制 | F4 只提供手动 `npm run sync:feedback`。公测期的用户反馈可能数日无人查看，与「M3 收集问题」的目标相悖。至少应提供轻量通知（邮件/Webhook/定时摘要） |
| P2-7 | 数据主体权利无入口 | GDPR/CCPA 的删除与更正请求缺少流程与联系人。§9 把「反馈状态流转」列为非目标尚可，但**数据主体删除请求是法定义务，不属于状态流转**，不能借非目标条款排除 |
| P2-8 | `Digest` 响应头已废弃 | §4.3 要求返回 `Digest` 响应头。RFC 3230 的 `Digest` 已被 RFC 9530 的 `Content-Digest` 取代，沿用旧头名会导致客户端与工具链不识别 |
| P2-9 | 字符计数口径未定义，且下限会挡掉合理短反馈 | §3.1 的「10～5000 个 Unicode 字符」未说明是 code point 还是 grapheme cluster，em 前段校验与后段校验极易不一致（emoji 单个即多 code point）；且 10 字符下限会拒绝「卡顿」这类完全合理的短反馈 |
| P2-10 | 缺少黑暗模式验收 | 浅色/暗色双主题是站点硬性基线（`WEBSITE_BUILD_PLAN.md` §4），但 §8 的人工视觉检查只列了桌面、390×844 移动端与阿拉伯语 RTL |
| P2-11 | 反馈页未规划 `noindex` | 计划全文未提及。用户反馈页被搜索引擎收录会污染 SEO 并暴露站点薄弱面 |
| P2-12 | 用户内容处置义务未定义 | 匿名公开上传面一旦被用于投放违法内容，站点缺少处置与上报流程。取消图片上传后该风险显著下降（仅剩文本），但仍需明确文本内容的处置责任 |
| P2-13 | 未衔接本仓两条既有硬约束，实现必踩 | ① `/{locale}/feedback` 必须通过 `npm run build` 的静态预渲染，页面读取 `sessionStorage` 时须用本仓既有的启动快照模式，否则触发 eslint 的 `react-hooks/set-state-in-effect`（error 级）；② 新增文案必须在 `src/i18n/dictionaries.ts` 补齐六语，否则触发字典一致性测试 |

### 3.4 P3（记录在案，随修复一并处理）

- **P3-1** §3.2 的 sessionStorage 决策悬空（原文「如确有排障价值，可使用」），F1 无对应验收条目。
- **P3-2** §4.2 只称 cursor「为服务端生成的不透明值」，未要求签名或校验，客户端可构造任意 cursor 造成跳过/重复（只读接口，风险低）。
- **P3-3** §4.2 未定义 `kind` 非法值的处理，也未给 `limit` 上限。
- **P3-4** §9 已诚实自述不支持多实例共享 artifact 索引，但该约束应前置到 §3.3 存储节提醒：当前服务为单进程内存态，日后启用 Redis Adapter/多实例时，feedback 存储必须同步迁移。
- **P3-5** `runtime-log` 文件名含 `server-<instanceId>`，但**未定义 instanceId 的稳定性**；若每次重启都变，清单文件数将持续膨胀。
- **P3-6** F5 仅泛提「备份」，未定义备份机制，而 feedback 目录是用户反馈的**唯一副本**。

## 4. 图片上传部分：专项记录

> 本节按用户要求单独成节，既记录**决策**，也完整保留**图片相关缺陷的提出**，两者不可互相替代。

### 4.1 用户决策（原文记录）

> 用户于 2026-09-15 明确表态：「关于图片的部分，我现在的想法是**先取消对图片上传的支持**。」

据此，首版 Feedback 功能**不实现截图上传**：§3.1 的 `screenshot` 字段、§3.3 目录结构中的 `screenshot.<ext>`、§4.1 中针对图片的全部校验与「解码后重新编码」要求、§4.2 `kind` 枚举中的 `screenshot`、§8 中「合法截图成功保存」「伪造 MIME、超限文件和不支持格式被拒绝」两条验收，以及 §6 中「拒绝 SVG/HTML 及可执行内容」的图片部分，**均应移出首版范围，并在 §9 非目标中写明**。

### 4.2 该决策消解的缺陷

| 缺陷 | 状态 |
| :--- | :--- |
| P1-4 中的「图像库选型」（sharp/jimp） | **消解**——无图片解码与重编码需求，不再需要引入重依赖 |
| P1-5 未剥离 EXIF/GPS（§4.1） | **消解**——无图片即无元数据夹带风险 |
| §4.1 的 magic bytes 校验、解码后像素尺寸上限、防伪装格式 / polyglot / 解压炸弹 | **消解**——无图片解析入口 |
| §4.1「整个请求最大 6 MiB」 | **可大幅收紧**——上限从 6 MiB 降至文本级别（建议 ≤1 MiB） |
| P2-12 的图片内容处置风险 | **显著下降**——上传面只剩文本，CSAM 类风险随之移除 |

### 4.3 该决策**未**消解、必须继续处理的缺陷

1. **P1-4 的另一半仍在**：只要保留 `clientLog` 附件，仍需 multipart 解析器选型。**但更彻底的简化路径值得评估**：若把 `clientLog` 作为 JSON 字符串字段随 `message`/`email` 一并提交，整个接口可从 `multipart/form-data` 改为 `application/json`，**完全不需要 multipart 解析器**，也彻底规避实测 B 的 `readJsonBody` 二进制陷阱。代价是需要新写一个带字节上限的 JSON body 读取函数（不可复用 4096 上限的 `readJsonBody`）。
2. **P0-1**（`.gitignore` 覆盖 `.jsonl` 与 `data/feedback/`）不受影响，仍需修。
3. **P0-2**（HTTPS 前置条件）不受影响 —— 邮箱与诊断日志仍是个人数据。
4. **P1-1 / P1-2 / P1-3 / P1-6** 与图片无关，全部仍需修。
5. **P2-4 / P2-5 / P2-6 / P2-7 / P2-9 / P2-11 / P2-12（文本部分）/ P2-13** 仍需处理。
6. §4.1 中「服务端不能信任浏览器声明的 MIME、扩展名、大小或 appVersion」——**图片项可删，但 `appVersion` 与 `clientLog` 大小仍不可信任**；且建议 `appVersion` 由服务端自行填入权威值（`/api/version` 已有真实来源），不采信客户端声明。
